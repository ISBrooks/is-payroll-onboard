# FieldRoutes Data Map — Discovery Notes

Every commission rule maps to FieldRoutes API data. These notes were verified
against the ORIGINAL company's FieldRoutes account. The API facts hold for any
account; the lists of service types, sources and ids are that company's, as
examples. Compare yours with `scripts/check_labels.py` after the backfill.

## API quirks (inherited, re-verified)

- `search` endpoints are **per-office** (`officeIDs` required or results
  silently drop / scope to office 1); `get` endpoints are global.
- A `get` with exactly one ID returns nothing — pad to two.
- Datetimes are **office-local** (`OFFICE_TIMEZONE`), not UTC.
- `search` result caps at 50k IDs per call — chunk date ranges.
- Some search filters are silently ignored (check `ignoredParams` in the
  response envelope) — e.g. `note/search` ignored `cancellationReasonID`.

## Entity chain for the commission engine

```
subscription ──soldBy──────────→ employee (rep)
     │ customerID
     ▼
customer  (aPay, autoPayPaymentProfileID, mostRecentCreditCardLastFour)
     │
subscription ──appointmentIDs / completedAppointmentIDs──→ appointment
                                                              │ ticketID
                                                              ▼
                                                           ticket (invoice)
                                                              │ ticketID
                                                              ▼
                                                        appliedPayment ──→ payment
```

### subscription (get: global; search filters: dateAdded, dateCancelled, dateUpdated)

Key fields (verified): `subscriptionID`, `customerID`, `officeID`, `soldBy`,
`contractValue`, `source`/`sourceID`, `serviceID` + `serviceType` (the
recurring service type), `dateAdded`, `dateCancelled`, `cancelledBy`,
`cxlNotes` (free text, NOT the structured reason), `active`/`activeText`
(cancelled shows "Frozen"), `initialAppointmentID`, `appointmentIDs`,
`completedAppointmentIDs` (comma lists — direct link to all services),
`autopayPaymentProfileID`, `billingFrequency`, `frequency`, `dateUpdated`.

`dateUpdated >= X` search per office = changed-since delta (rep edits,
cancels, value changes, reactivations of ANY age flow in) — pattern proven
in the ISA dashboard nightly sync.

### appointment (get: global)

`appointmentID`, `subscriptionID`, `customerID`, `type` (serviceType ID),
`status`/`statusText` ("Completed"), `date`, `dateCompleted`, `ticketID`,
`isInitial` ("1" on the initial), `servicedBy`, `dateUpdated`.
Sample verified: a sub's initial appointment → statusText Completed, with
its ticketID.

### ticket = invoice (get: global; search by invoiceDate/dateUpdated)

`ticketID`, `appointmentID`, `customerID`, `subscriptionID` (often "0" —
join via appointment instead), `total`, `balance`, `serviceCharge`,
`invoiceDate`. **Paid ⇔ balance == 0.00** (guard against write-offs via
payment records).

### appliedPayment (search: officeIDs + dateApplied; get: global)

`appliedPaymentID`, `paymentID`, `ticketID`, `customerID`, `dateApplied`,
`appliedAmount`, `taxCollected`. This gives the **date a ticket became
paid** — the commission trigger date.

### payment (search: officeIDs + date; get: global)

`paymentID`, `customerID`, `date`, `amount`, `appliedAmount`, `status`,
`writeOff` (exclude), `creditMemo`, `invoiceIDs`, `lastFour`,
`paymentMethod`, `originalPaymentID` (reversals/refunds reference the
original). **`payment/get` embeds `paymentApplications`** —
`[{ticketID, dateApplied, appliedAmount, taxCollected}]` (verified) — so
pulling a customer's payments (IDs from `customer.paymentIDs`) yields every
ticket's payment dates without touching the appliedPayment endpoint.

### Invoice ↔ subscription linkage (verified on monthly-billed sub 900004)

Two kinds of subscription invoices:
- **Service-tied:** `ticket.appointmentID` set → join appointment →
  subscriptionID. On monthly-billed accounts these are usually **$0**
  (the visit itself doesn't bill).
- **Monthly auto-generated:** `ticket.autoGeneratedType = 'RECURRING'` and
  **`ticket.autoGenerated` = the subscriptionID** (not a boolean!).
  `appointmentID` is 0.
`ticket.subscriptionID` itself is unreliable (often "0") — never join on it.

### Billing frequency semantics (verified subs 900004, 900018)

`recurringCharge` is the amount per **billing period**, not per service:
- 900004: BIMONTHLY PEST, frequency=60, billingFrequency=30,
  recurringCharge=$59 → $59/month invoices, per-service value **$118**.
- 900018: frequency=60, billingFrequency=60, recurringCharge=$75 →
  bill-at-service, per-service value $75.

    per_service_value = recurringCharge × frequency / billingFrequency
                        (billingFrequency > 0; else = recurringCharge)

billingFrequency values seen: -1 (bill at service), 0, 28, 30, 60, 90, 360.
Treat ≤ 0 as bill-at-service. RULES §4b coverage target =
2 × per_service_value.

### Rep mapping (seed from the IS Dashboard)

`data/isadash.sqlite` table `agent_map` (`on_roster=1`) maps each roster
agent → comma list of FR employee IDs (one per office, e.g. Avery Stone → 9 IDs). Seed from there; resolve unknown `soldBy` IDs via
`employee/get` + roster-name match (`config/name_overrides.json` pattern).

### customer (get: global)

Card-on-file rule (proven in dashboard backfill_autopay.py):
`card_on_file = (autoPayPaymentProfileID not in ("", "0"))
             or (mostRecentCreditCardLastFour nonempty)`.
`aPay != "No"` = autopay enrollment — NOT the commission signal (rule cares
only that a payment method is saved). Also: `status`/`statusText`,
`dateCancelled`, `balance`, `subscriptionIDs`, `appointmentIDs`.

### Cancellation reason — lives on NOTES, not the subscription

`note` entity: cancel writes a note with `type` = "Subscription Cancel"
(`typeID` 16), `referenceID` = **subscriptionID**, `cancellationReason` =
text (e.g. **"Renewal"**), `date` = cancel timestamp.
Verified on subscriptions cancelled with reason "Renewal".

- `note/search` supports officeIDs, customerIDs, dateAdded; the
  `cancellationReasonID` filter is IGNORED (check `ignoredParams`) — filter
  client-side or by typeID if honored.
- Global cancellationReason list: search officeIDs=-1 → 49 IDs; `get` on
  those IDs returns empty (endpoint quirk) — reason TEXT comes on the note
  itself, which is all we need.

### serviceType (get by typeIDs; search per office misses global -1 rows)

The original account's list (yours will differ). Highlights:
- "Initial Service": ids 2 (global) + per-office 5,8,27,33,37,40,58,61,65 — `initial=1`
- "Reservice": ids 3 (global) + 6,9,29,34,38,41,59,62,66 — `reservice=1`  → NEVER qualifying
- "General Service": ids 1,23 (global) + 4,7,32,36,39,57,60,64 → NEVER qualifying
- Recurring plan types (qualifying when they match the sub's serviceID):
  MONTHLY PEST 19, BIMONTHLY PEST 13, QUARTERLY PEST 20, MONTHLY/BIMONTHLY
  GOPHER 24/25, BIMONTHLY RODENT 14, PEST & MOSQUITO/GOPHER combos
  45,46,47,48,76,77, 12/8 MONTH MOSQUITO 10/11, etc.
- Junk types to ignore: Bounced Check Fee 30, Cancellation Charge 26,
  Collect Payment 17, Collections Late Fee 53, Overdraft Fee 74,
  Technician Tip 28, Inspection 35, tests 44/72/78.

Qualifying-service test = appointment Completed AND (isInitial=1 OR
appointment.type == subscription.serviceID). (Matches the rule doc §4.)

### Sources (the original account's exact strings)

5% sources: "Mosquito upsell Campaign" and EVERY renewal source — any name
containing "Renewal" ("Inside Sales Renewal", "Bad Debt Renewal",
"Renewal - In/Out of/No Contract", "Rate Raise Renewal", "ZOLD - Renewal");
owner 2026-10-14. "Upsell" is 5% only on 8/12-month mosquito subs.

### Rep identity

`subscription.soldBy` → FR employee ID; `employee/get` → fname/lname.
One human ↔ MULTIPLE FR employee IDs (one per office). The roster comes from the
dashboard's Payroll → Commission Roster; name-based mapping logic and `agent_map` data can
be seeded from the IS Dashboard (`data/isadash.sqlite`, `agent_map` +
`employees` tables, `config/name_overrides.json`).
